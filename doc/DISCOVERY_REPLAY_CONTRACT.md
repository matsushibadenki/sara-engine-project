# Discovery Replay Contract v1

This is an observed-only research-orchestration primitive inspired by [Dream-RSI](https://github.com/zhengkid/Dream-RSI/blob/main/papers/Dream-RSI.pdf). It does not change SARA's neural learning, Event Memory replay, evaluator, or production behavior.

## Record and visibility

`ReplayRecord` is a frozen, versioned tree-node shape. Each record carries a contiguous sequence number, opaque node and parent IDs, hypothesis and policy IDs, SHA-256 candidate/source/preregistration identities, one fixed evaluator ID, a split, outcome status/score, and nonnegative CPU/event/state costs. Valid and negative-gate outcomes retain finite measured scores; execution failures and explicitly missing outcomes carry no score. Missing means a recorded action has no usable outcome; it is not a negative result. The root has no parent, result, or cost. Non-root records have an earlier parent; only the root may start multiple branches, and each non-root branch has at most one recorded continuation. The implementation accepts development trees only.

`DiscoveryReplayWorld.view` returns revealed records plus `available_actions`: visible parent IDs for which one recorded continuation can still be revealed within the budget. It never exposes a hidden child ID, outcome, score, or number of remaining root branches. A policy should receive this view, not the world object or the complete tree. Selecting the root reveals the next recorded independent branch; selecting a visible branch tip reveals its one recorded continuation. Duplicate, invisible, terminal, unsupported, oversized, or over-budget selections fail before any state changes. An empty selection stops the rollout. No node outcome is synthesized for an unrecorded action. **The availability list is a retrospective recorded-support oracle:** whether a historical branch was continued may not have been knowable to a prospective researcher. Policy comparisons must give every arm the same oracle and cannot claim prospective validity from it alone.

## Bounds and exclusions

Defaults are at most 1,024 recorded nodes, eight actions per decision, and 128 revealed nodes. Callers may set smaller positive limits. All records in a tree must use the same evaluator ID; `heldout` records are rejected. `run_replay_policy` passes only `ReplayView` to a policy and caps decision rounds. It neither schedules experiments nor compares policies. No replay result authorizes changing a frozen benchmark, launching an experiment, or deploying a policy.

## Managed journal

`DiscoveryJournal` accepts only `.jsonl` paths under `workspace/`. Each canonical line contains exactly one v1 record, the preceding line hash, and its own SHA-256 digest. Append operations take an exclusive file lock, validate the complete prior prefix and tree, enforce a 1,024-record/4 MiB journal limit, then append and sync. A batch is fully validated before the write, but its disk append is not crash-atomic. Invalid, incomplete, noncanonical, duplicate-key, oversized, or held-out content fails closed. A returned head hash can be pinned elsewhere; `load` and `append` optionally require that expected head, detecting a stale or wholesale rewritten chain. A SHA chain without an independently pinned head is **not** authentication against a malicious full rewrite. An interrupted short write may leave a partial last line; it is rejected, not silently repaired.

## Prospective decision capture

`DiscoveryCaptureLog` is a separate, development-only `workspace/` JSONL log for future experiments. It records a `CaptureIntent` with parent choice, hypothesis/policy ID, candidate/preregistration digest, and evaluator identity **before** accepting a `CaptureOutcome` with status, score, and bounded CPU/event/state cost. The first intent is a root without an outcome. A child intent requires an already completed parent outcome, except that independent branches may start from the root. Pending intents survive reload; outcome-first, duplicate, mismatched, unsupported, or held-out events fail before append. Every line is canonical and hash-chained, with a lock, size bound, sync, and optional expected-head compare-and-swap.

`project_source_snapshot` can derive an in-memory, unapproved source-snapshot JSON only when every intent has an outcome and the caller supplies the exact current capture head. It carries recorded scores and costs without inventing a result for pending actions. The method does not publish a file or review receipt, and a caller-supplied head is not independently pinned evidence.

`run_captured_development_action` is the optional integration boundary for a future development runner: it durably appends the intent before calling a supplied evaluator, then appends only a matching `CaptureOutcome` under the intent-head compare-and-swap. If the evaluator raises, returns a mismatched result, or another writer changes the head, the intent remains pending for explicit inspection. The evaluator must measure and supply its own score and CPU/event/state costs; the adapter does not infer them or manufacture a failure result. The fixed synthetic smoke runner uses this adapter without changing a frozen benchmark or promoting a result.

The capture adapter has now been exercised once through a separate fixed synthetic development [smoke runner](DISCOVERY_CAPTURE_SMOKE_RESULT.md). This verifies the instrumentation path, not genuine multi-branch research exploration; no real research-history tree has been reviewed or exported. It does not bypass the independent original-to-snapshot review gate. Hash chaining proves neither wall-clock order nor authenticity against a full log rewrite without an externally pinned head; event timestamps or external attestation are not implemented. A partially written last line fails closed.

## Reviewed export and post-run audit

`ExportReviewReceipt` binds a declared reviewer, source digest, and digest of one sanitized development tree. `export_reviewed_tree` requires a source JSON snapshot: it checks the file's SHA-256 against the receipt, reconstructs every `ReplayRecord` from the snapshot, and requires an exact tree-digest match before writing into an empty managed journal under a genesis-head compare-and-swap. The `sara-discovery-source-snapshot-v1` format has exactly `schema`, `split`, and `records`; each record has the complete replay fields except `source_sha256`, which is filled from the snapshot file's hash to avoid self-reference. `audit_source_material` accepts only bounded JSON files under managed development directories with `"split": "development"`; duplicate keys, extra fields, invalid trees, and known held-out/sealed-test markers fail closed. This proves consistency with the sanitized snapshot, **not** that the snapshot faithfully represents the original experimental history or is fully redacted. The BPI and Sepsis **final-test result reports** lack a development-only declaration and contain `frozen_test` results, so they are not eligible source histories for this replay path. This is a programmatic approval gate, **not proof of human review**: receipts are neither signed nor independently authenticated. No existing experiment histories have been reviewed or imported by this implementation. A human must inspect original-to-snapshot provenance, redaction, split isolation, and the opaque IDs before issuing a receipt, then independently pin the resulting head hash.

`audit_replay` is an operator-only post-run inspection, never policy input. It reports recorded versus revealed non-root nodes, coverage, unrevealed nodes, missing and failed outcomes, and a lower bound on nodes structurally unreachable under the reveal budget. The lower bound assumes the shortest valid reveal path and is not a counterfactual estimate of what an untried policy would discover. The controller passes a `ReplayView` containing only currently revealed records, and hidden-node actions fail. That interface-level check does **not** prevent a Python policy closure or external process from reading the source tree out of band. Run policies in an isolated environment and audit their inputs before making unavailable-information claims.

`run_traced_replay_policy` starts from a fresh world and records a digest of the exact view (including available-action support) supplied at each decision, the chosen actions, newly revealed node IDs, and the resulting view digest. `verify_replay_transcript` reconstructs each transition from the bound tree and rejects hidden actions, forged reveals, or mismatched views. A transcript is a reproducibility and interface-availability check, not proof that the policy did not read hidden data through a closure, filesystem, network, or another process. No isolated execution boundary is implemented yet.

The currently inspected BPI/Sepsis final-test reports and training-only diagnostic summaries contain aggregate outcomes rather than a per-decision exploration tree with parent choice, candidate/evaluator identity, observed outcome, and cost. They cannot be converted into policy-comparison trajectories without inventing missing actions. Capture such decisions prospectively in future development experiments, then perform original-to-snapshot review before export.

The strict record allowlist excludes free-text evidence and source content, but opaque IDs can still encode sensitive information. Add task-family/time/source split isolation, independent source-redaction review, isolated-policy leakage checks, and prospective validation before any policy optimization claim.
